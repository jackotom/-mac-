# v0.3.0 可信对局上下文升级计划

## 完成标准

- 原 v0.2.9 项目和安装包不改动，全部工作位于独立 worktree。
- 从真实 `Power.log` 读取回合、行动方、法力上限和已用法力。
- 证据不足时省略字段，禁止显示 `?`、禁止按单双回合猜行动方。
- 已使用、疑似烧毁和实时事件带真实回合信息。
- 主窗口和 100px 我方小窗显示紧凑对局状态；新局、停更、结束时清空。
- 竞技场三选一保持游戏左中右顺序；进入实战后恢复对手记录。
- 星空投影球详情显示本局已施放法术总数和已识别明细；总数大于明细时明确标记不完整。
- 我方牌库按法力值从低到高排列；其它区域保留真实区域或历史顺序。
- 对手窄长窗口的计数器和卡牌分组连续排列，不得被剩余高度拉出巨大空白。
- 按来源显示牌库创建牌的剩余数量；双倍触发和后续抽取必须实时增减。
- 置顶、置底显示真实牌名；洗牌后位置记录消失，但来源数量和普通牌库牌名保留。
- 现有古神、双倍施放、嵌套古神、烧毁、奥秘和窗口契约不退化。
- 定向测试、全量测试、类型检查、构建、真实日志回放和 Electron 窗口检查全部通过。

## 第一版方案

新增“对局洞察”，一次加入抽牌概率、对手套牌推测、斩杀提示、风险提醒、完整回放和历史趋势。

## 第一轮毒舌审查

这不是升级，是功能垃圾桶。

- 当前回合仍是 `?`，却要做套牌推测和斩杀提示，属于拿猜测冒充智能。
- 100px 小窗已接近信息极限，再塞概率和建议只会遮挡游戏。
- 当前历史最多 100 局且字段贫乏，所谓长期趋势和完整回放没有可信数据。
- 再加一级入口只会扩大已经臃肿的 `App.tsx`。
- 六个半成品一起做，最终大概率得到一个更大的半成品。

结论：整版否决。

## 第二版方案

建立统一日志内核，一次替换两套 Power 解析、文件游标、状态引擎、事件库、断点恢复、来源谱系和全部历史。

## 第二轮毒舌审查

方向比第一版诚实，实施范围仍然失控。

- 一次替换五千多行核心逻辑，是拿刚修好的古神和烧毁功能赌运气。
- “插件化”和“完整事件库”没有当前用户价值，只是架构上瘾。
- 事件语义尚未统一，先做持久化只会永久保存错误。
- 大重写会让用户长期看不到任何新功能。

结论：保留统一事实模型思想，砍掉一次性重写。

## 最终设计

### 深模块：`MatchFlow`

接口只暴露当前可信事实：

```ts
interface MatchFlow {
  accept(event: ParsedLogEvent): void;
  snapshot(): MatchFlowSnapshot | undefined;
}
```

实现内部隐藏：

- GameEntity 全局回合。
- 玩家实体的当前回合、行动权、法力上限和已用法力。
- 玩家名称、PlayerID 与本地 controller 的映射。
- 重复 GameState / PowerTaskList 输出。
- 开局、换局、结束和停更清理。
- 缺证据时的字段降级。

`TrackerEngine` 仍是卡牌位置与动作历史的唯一事实来源。`MatchFlow` 只负责对局时间坐标，不建立第二套卡牌状态。

### 公开状态

```ts
interface MatchFlowSnapshot {
  readonly globalTurn?: number;
  readonly activeSide?: "friendly" | "opponent";
  readonly phase?: "mulligan" | "start" | "action" | "end";
  readonly friendly?: PlayerTurnState;
  readonly opponent?: PlayerTurnState;
}

interface PlayerTurnState {
  readonly turn?: number;
  readonly mana?: number;
  readonly manaUsed?: number;
}
```

所有字段可选。未知就是不显示。

### 界面

- 主窗口：`第7回合 · 我方行动 · 法力5/7`，替换没有价值的“监听中”占位。
- 100px 我方小窗：单行 `7回 · 我 · 5/7`，高度不超过 18px。
- 250px 对手窗：只显示“我方回合 / 对手回合”，不重复法力。
- 已使用、疑似烧毁、事件流：显示 `第N回合`；未知时不显示回合标签。
- 竞技场三选一不排序，只给最佳牌增加“首选”。
- `arena.status === "playing"` 时主窗口显示对手记录，不显示选牌等待文案。

## 实施任务

1. 后端：解析 `TURN / STEP / NEXT_STEP / CURRENT_PLAYER / RESOURCES / RESOURCES_USED`。
2. 后端：实现 `MatchFlow`，接入 `TrackerEngine`，处理重置、结束和重复日志。
3. 后端：为 used、burned、events 增加可选回合字段并补运行时校验。
4. 前端：实现统一 `MatchPulse`，接入主窗口、我方小窗和对手窗。
5. 前端：实时事件和历史项显示可信回合。
6. UI：竞技场保持左中右顺序；实战恢复对手面板。
7. 详情：恢复双方隔离的本局动态卡牌资料，修复星空投影球。
8. 排序：仅牌库分组按费用、牌名和未知费用规则排序。
9. 布局：覆盖无回合状态条但有公共计数器的对手窄窗。
10. 文档与版本：验收通过后升到 `0.3.0`。
11. 牌库插入：解析 `DISPLAYED_CREATOR / ZONE_POSITION / SHUFFLE_DECK`，分别维护来源数量和位置。
12. 牌库插入 UI：来源严格显示两行“来源创建 / N张卡牌”，不在统计块展开具体生成牌。

## 测试边界

- GameState 与 PowerTaskList 重复同一状态。
- 额外回合、连续同一玩家回合、回合号缺失。
- 行动方已知但回合未知；回合已知但行动方未知。
- 法力字段缺失、乱序、负数和大于上限。
- 新局、日志截断、停更和结束后旧值不得残留。
- 双倍古神、嵌套古神、回手再用、十张手牌烧毁不退化。
- 100×200、100×834、100×900 逻辑布局无横向滚动。
- 900×620 主窗口无整页溢出。
- 投影球总数 7、已识别 4 时显示 `已识别 4/7`，不得补造三张牌。
- 同一张动态卡牌在双方出现时，本局详情不得串到另一方。
- 牌库费用顺序为已知费用升序、同费牌名升序、未知费用最后。
- 对手窗 `196×834` 且有计数器、无回合状态条时，计数器区域高度不超过 31px。
- 同一来源生成 10 张时显示 10，抽一张变 9；已知生成牌仍出现在普通牌库列表。
- 洗牌后置顶、置底块完全消失，来源统计数量不变。
